# Разбор дефектов, найденных при тестировании Этапа 5 — подробно, для новичка

Этот документ объясняет три бага, которые автоматические тесты нашли в
`Extraction/zapolnenie.lsp`, и четыре наблюдения, которые исправлять не стали.
Всё рассказано «с нуля»: как устроен код, в чём именно была ошибка, как она
выглядела на числах и почему исправление правильное.

---

## 0. Мини-шпаргалка по AutoLISP, чтобы читать дальше

Почти весь код задачи «Заполнение» работает со **списками** — главной
структурой данных языка. Запись об одной панели внутри агрегата выглядит так:

```lisp
("ВИТРАЖ В-2|1526|626" "Витраж В-2" 1526 626 1)
;        ↑                  ↑          ↑    ↑   ↑
;       ключ               тип       выс. шир. кол-во
```

Достают элементы функциями семейства `car`, `cadr`, ... Читаются они просто:
буквы `A` и `D` между `C` и `R` — это цепочка `car`/`cdr`, применяемая
**справа налево**. `car` берёт первый элемент, `cdr` — «хвост» списка без
первого элемента:

| Функция              | Расшифровка                     | Что вернёт для записи выше |
|----------------------|---------------------------------|----------------------------|
| `(car x)`            | 1-й элемент                     | ключ `"ВИТРАЖ В-2|1526|626"` |
| `(cadr x)`           | `car(cdr(x))` — 2-й элемент     | тип `"Витраж В-2"`           |
| `(caddr x)`          | `car(cdr(cdr(x)))` — 3-й        | высота `1526`                |
| `(cadddr x)`         | `car(cdr(cdr(cdr(x))))` — 4-й   | ширина `626`                 |
| `(car (cddddr x))`   | убрать 4 элемента, взять 5-й    | количество `1`               |

Ещё пригодятся:
- `(assoc КЛЮЧ список)` — находит в списке первую запись с таким `car`;
- `(subst НОВОЕ СТАРОЕ список)` — заменяет элемент `СТАРОЕ` на `НОВОЕ`;
- `vl-sort список предикат` — сортировка; предикат `(a b)` должен отвечать,
  «a идёт раньше b?»;
- `'ТИП` — это *ключ* записи, уникальная строка `"ТИП|ВЫСОТА|ШИРИНА"`,
  по которой агрегат понимает, что две панели «одинаковые».

## Баг №1 (критичный). Повторяющиеся панели считались как «ширина + 1»

### Как должно работать

Функция `zapolnenie-aggregate` обходит все найденные блоки и складывает
одинаковые панели в одну запись, увеличивая счётчик:

1. панель встретилась впервые → создаём запись
   `(ключ тип высота ширина 1)`;
2. панель с таким же ключом уже есть → заменяем запись на такую же,
   но `количество + 1`.

### Где была ошибка

Код «увеличения количества» выглядел так:

```lisp
(if found
  (setq acc (subst
              (list key (cadr found) (caddr found) (cadddr found) (1+ (cadddr found)))
              found
              acc))
```

Смотрим внимательно на последний элемент новой записи:
`(1+ (cadddr found))`. По таблице выше `(cadddr found)` — это **4-й элемент —
ширина**, а не 5-й — количество! То есть при каждом повторе вместо
`количество + 1` код записывал `ширина + 1`.

### Как это выглядело на числах (реальный прогон до исправления)

Фикстурный чертёж: две одинаковые панели «Витраж В-2» 1526×626,
три одинаковые «Стойка A» 2026×1026.

```
Ожидалось:   ("Витраж В-2" 1526 626 2)   ("Стойка A" 2026 1026 3)
Получалось:  ("Витраж В-2" 1526 626 627) ("Стойка A" 2026 1026 1027)
;                                     ↑   627 = 626 + 1!      ↑ 1027 = 1026 + 1!
```

Дальше ошибка размножалась: количество входит формулой в площадь каждой
записи (`В × Ш × кол-во / 1 000 000`), в итоговое «элементов N» и в общую
площадь — т.е. **все отчёты (XLS, CSV, GAL, таблица, консоль) для любого
чертежа с повторяющимися панелями содержали нереальные числа**: «627 шт.»,
площадь в сотни квадратных метров там, где их два квадрата.

Почему это не заметили на этапах 1–4: если каждая панель в чертеже
уникальна (не повторяется), ветка «увеличить количество» не выполняется
ни разу — и всё выглядит правильно.

### Исправление

```lisp
(list key (cadr found) (caddr found) (cadddr found)
      (1+ (car (cddddr found))))     ; 5-й элемент — настоящий счётчик
```

`(cddddr found)` отрезает первые 4 элемента (остаётся список из одного —
счётчика), `car` его достаёт. После правки прогон даёт ровно ожидаемые
2 и 3 шт., итоги «элементов 9, общая площадь 10.96 м²».

## Баг №2. Сортировка DETAIL: размеры одного типа шли «по буквам», а не по величине

### Как должно работать

Требование (из спецификации задачи): сортировка DETAIL —
**Тип → Высота → Ширина** (по алфавиту, затем по возрастанию). После
агрегации записи сортируются через `(vl-sort acc 'zapolnenie-sort-less)`,
где `zapolnenie-sort-less a b` отвечает «запись a должна идти раньше b?».

### Где была ошибка

На вход предиката приходят те же 5-элементные записи
`(ключ тип высота ширина кол-во)`. А код читал поля так:

```lisp
(defun zapolnenie-sort-less (a b / ta tb ha hb wa wb)
  (setq ta (strcase (car a))     ; ← car — это КЛЮЧ, а не тип!
        tb (strcase (car b))
        ha (cadr a)              ; ← cadr — это ТИП (строка), а не высота!
        hb (cadr b)
        wa (caddr a)             ; ← caddr — это ВЫСОТА, а не ширина!
        wb (caddr b))
```

На одну позицию сдвинуто всё. Из-за этого:

- Группировка по типу **случайно сохранялась**: ключ начинается с имени
  типа (`"СТОЙКА A|1826|826"`), поэтому «по алфавиту» записи группировались
  верно, и баг был неброским.
- А вот внутри типа сравнение шло по *строковым ключам*. Строки
  `"ПАНЕЛЬ АМ45|1226|526"` и `"ПАНЕЛЬ АМ45|526|1226"` сравниваются по
  символам: первый отличающийся символ — это `'1'` против `'5'`, а `'1' < '5'`.
  Итог: **высота 1226 мм печаталась раньше 526 мм**. Числовое сравнение
  дало бы наоборот (526 < 1226). Числа с одинаковым количеством цифр
  лексикографически сортируются правильно — поэтому на «круглых» тестовых
  данных (2000 и 1800) ничего не бросалось в глаза.

Зонд X.1 (`zapolnenie-aggregate` на паре панелей 1200↔500) до исправления
выдавал порядок `(1226, 526)` — перевернутый.

### Исправление

```lisp
(setq ta (strcase (cadr a))     ; тип      — 2-й элемент
      tb (strcase (cadr b))
      ha (caddr a)              ; высота   — 3-й элемент (число!)
      hb (caddr b)
      wa (cadddr a)             ; ширина   — 4-й элемент (число!)
      wb (cadddr b))
```

Теперь сравнения высот и ширин — числовые, зонд выдаёт `(526, 1226)` —
как требует спецификация. Порядок строк виден пользователю в таблице
AutoCAD и в строках GAL-файла, поэтому это не «косметика»: раскройный
лист для станка читается в этом порядке.

## Баг №3. Слой после запятой с пробелом не находился (тесты 1.3/1.4 плана)

### Как должно работать

Автономная команда `ZAPOLNENIE` в начале спрашивает:

```
Введите слои через запятую (Enter — все слои):
```

Пользователь естественно пишет с пробелом: `Заполнение, Стекло`.

### Где была ошибка

Строка из `getstring` возвращается как набрана — **с пробелом**. Разбор
делал `split-string`:

```lisp
(split-string "Заполнение, Стекло" ",")
; → ("Заполнение" " Стекло")
;                    ↑ ведущий пробел остался в имени!
```

Дальше имена используются дважды, и оба раза нужно **точное** совпадение
(проверка без учёта регистра, но не без учёта пробелов):

1. строится фильтр `ssget`: слои `"ЗАПОЛНЕНИЕ, СТЕКЛО"` — AutoCAD ищет слой
   буквально с ведущим пробелом « СТЕКЛО», такого нет;
2. вторая проверка `su-layer-selected-p` сравнивает имя слоя блока
   с `" СТЕКЛО"` — снова не совпадает.

Итог: ввод `Заполнение, Стекло` выбирал блоки **только со слоя
«Заполнение»** — тест 1.3 из плана проваливался (ожидалось 6 элементов
с двух слоёв, находилось 4 с одного). Тот же эффект был в 1.4. Ввод без
пробела (`Заполнение,Стекло`) работал — поэтому баг мог годами жить
незамеченным, все просто привыкли не ставить пробел.

### Исправление

```lisp
(setq layers (mapcar 'strcase
                     (mapcar '(lambda (s) (vl-string-trim " \t" s))
                             (split-string layers-str ","))))
```

Каждому имени срезаются пробелы и табуляции по краям. Пробелы **внутри**
имени («Заполнение витражей») не трогаются — команда намеренно вызывает
`getstring T` (разрешающий пробелы), и тест 1.4 как раз проверяет, что
такие имена не «рвут» ввод.

## Наблюдения — то, что осталось как есть (и почему)

### 1. Та же «пробельная» ситуация в `c:fasonka` и `c:subsystem`

Обе команды разбирают ввод слоёв тем же `split-string` из
`common/task-utils.lsp` без очистки. Это **унаследованное** поведение, а не
поломка Этапов 1–4, и регрессионные тесты (группа 6) его зафиксировали как
«работает как раньше». Исправлять правильнее отдельным решением — точечно
в этих командах или централизованно в `split-string`/`tu-parse-comma-list`
(последний уже умеет обрезать пробелы), с прогоном всех задач.

### 2. «Сохранить как...»: имя вида `имя_по_выбору.xls подробный.xls`

Когда в диспетчере выбирают «Сохранить как...», системный `getfiled`
возвращает полный путь **с расширением** (`...\имя_по_выбору.xls`). Общий
код задач дописывает к этой строке суффикс режима и расширение:
`имя_по_выбору.xls подробный.xls`. Файл сохраняется точно по выбранному
пути, имя начинается выбранным именем — функционально всё работает,
выглядит лишь непривычно. Так делают все три задачи (общий код), поэтому
чтобы не менять поведение Фасонки/Подсистемы в скоупе Этапа 5, оставлено;
если исправлять — то отдельно и для всех задач сразу (обрезать расширение
у базы).

### 3. Фасонка переспрашивает «Создать таблицу AutoCAD? [Yes/No]»

При запуске через диспетчер с включённым «AutoCAD» Фасонка всё равно
задаёт в командной строке вопрос `Создать таблицу AutoCAD? [Yes/No]
<Yes>` — так написана `common/table-utils.lsp` (`tbl-create-table`). Это
ожидаемое поведение («как раньше»): пользователь жмёт Enter, и таблица
создаётся. Тест 6.3 это учитывает. Изменение (не спрашивать, если флаг
уже выбран в диспетчере) — отдельная UX-правка, не относящаяся к
«Заполнению».

### 4. Файл `.xls` — это XML, а не бинарный формат Excel

Экспорт пишет формат **XML Spreadsheet 2003** с расширением `.xls`. Excel
открывает такой файл как полноценную таблицу (со стилями, формулами
`ss:Formula`, объединёнными ячейками), но при открытии может показать
предупреждение, что содержимое не соответствует расширению — это нормально
и не влияет на данные. Ровно так же сделаны Фасонка и Подсистема — то есть
единый стиль проекта соблюдён. GAL и CSV — обычные текстовые файлы в
кодировке Windows-1251, что проверено побайтово в тестах.

## Как эти баги были найдены

Все три воспроизвелись автоматически, без AutoCAD: реальные
`zapolnenie.lsp` + `common/*.lsp` исполнялись интерпретатором
(`tests/autolisp.py`) на mock-чертеже с известными панелями
(`tests/acad_mocks.py`):

- Баг №1 всплыл мгновенно: вместо ожидаемых «2 шт.» контрольная цифра
  показала «627» (а «ширина» фикстуры — 626).
- Баг №2 подтвердил специальный **зонд X.1**: агрегат на паре панелей
  с высотами 526/1226 выдал перевёрнутый порядок.
- Баг №3 — это буквально тест-кейсы 1.3/1.4 из плана Этапа 5: вводились
  строки `Заполнение, Стекло` и `Заполнение витражей, Стекло`.

После точечных правок (1 файл, +15/−9) полный прогон — **22/22 PASS**,
зонды X.1/X.2 — PASS. Протокол: `tests/stage5_report.md`;
запуск: см. `tests/ЗАПУСК-ТЕСТОВ.md`.
